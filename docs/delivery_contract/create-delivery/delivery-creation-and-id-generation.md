
# Delivery Creation and Automatic ID Generation

## Overview

The `create_delivery` entry point creates a new delivery record in the delivery contract. It requires the sender's authorization, generates a new delivery identifier using a persistent counter, stores the delivery metadata and initial delivery state, and publishes a creation event.

Implementation reference: `contracts/delivery_contract/lib.rs`.

## Function Signature

```rust
pub fn create_delivery(
    env: Env,
    sender: Address,
    recipient: Address,
    metadata: DeliveryMetadata,
) -> DeliveryId
```

| Parameter | Type | Description |
|---|---|---|
| `env` | `Env` | Soroban environment used for storage, ledger timestamp, and events. |
| `sender` | `Address` | Address creating the delivery request. |
| `recipient` | `Address` | Address expected to receive the delivery. |
| `metadata` | `DeliveryMetadata` | Cargo and delivery information stored with the delivery record. |

The function returns the newly generated `DeliveryId`.

## Authorization

The sender must authorize the transaction:

```rust
sender.require_auth();
```

This prevents an unauthenticated account from creating a delivery on behalf of another sender.

## Automatic Delivery ID Generation

Delivery identifiers are generated using the persistent `DataKey::DeliveryCounter`.

The function reads the current counter:

```rust
let mut counter: u64 = env
    .storage()
    .persistent()
    .get(&DataKey::DeliveryCounter)
    .unwrap_or(0);
```

It increments the counter:

```rust
counter += 1;
```

It then stores the updated value:

```rust
env.storage()
    .persistent()
    .set(&DataKey::DeliveryCounter, &counter);
```

Finally, it converts the counter into the shared `DeliveryId` type:

```rust
let delivery_id = DeliveryId::from(counter);
```

The counter is initialized to `0` by `delivery_contract::init`. Consequently, the first successful creation uses ID `1`, followed by `2`, `3`, and so on.

The identifier is generated by the contract rather than supplied as a separate function argument.

## Delivery Metadata

The metadata parameter uses the shared `DeliveryMetadata` structure from `contracts/shared_types/lib.rs`.

Its fields are:

| Field | Type | Description |
|---|---|---|
| `delivery_id` | `u64` | Delivery identifier field carried by the metadata object. |
| `origin` | `String` | Delivery origin information. |
| `destination` | `String` | Delivery destination information. |
| `cargo_description` | `CargoDescriptor` | Structured description of the cargo. |
| `created_at` | `u64` | Timestamp field carried in the metadata. |
| `estimated_delivery` | `u64` | Estimated delivery timestamp carried in the metadata. |

The `CargoDescriptor` structure contains:

| Field | Type | Description |
|---|---|---|
| `weight_grams` | `u32` | Cargo weight in grams. |
| `category` | `CargoCategory` | Cargo classification. |
| `fragile` | `bool` | Indicates whether the cargo is marked as fragile. |

The available `CargoCategory` variants are:

- `Documents`
- `Electronics`
- `Perishables`
- `Clothing`
- `General`

The delivery contract stores the supplied metadata in the delivery record. It does not reconstruct the metadata or automatically replace its fields with the generated ID or current ledger timestamp.

**Important:** The generated `DeliveryRecord.delivery_id` is the authoritative identifier returned by `create_delivery`. The current implementation does not validate that `metadata.delivery_id` matches that generated identifier. Callers should therefore supply consistent metadata, and integrations should use the returned `DeliveryId` for subsequent operations.

## Initial Delivery Record

After generating the ID, the function creates a `DeliveryRecord`:

```rust
let record = DeliveryRecord {
    delivery_id,
    sender: sender.clone(),
    recipient,
    driver: None,
    status: DeliveryStatus::Pending,
    metadata,
    created_at: env.ledger().timestamp(),
    delivered_at: None,
    transit_started_at: None,
};
```

The initial record contains:

- The generated delivery ID.
- The sender and recipient addresses.
- No assigned driver.
- An initial status of `Pending`.
- The supplied metadata.
- The current ledger timestamp as the record's `created_at`.
- No delivery completion timestamp.
- No transit start timestamp.

## Persistent Storage

The record is stored using the shared `delivery_key` helper:

```rust
let key = delivery_key(delivery_id);
env.storage().persistent().set(&key, &record);
env.storage().persistent().extend_ttl(&key, 518400, 518400);
```

The helper constructs a `StorageKey::Delivery` key for the generated ID.

The record is stored in persistent storage and its TTL is extended after creation.

## Creation Event

After storing the record, the contract publishes:

```rust
env.events().publish(
    (soroban_sdk::Symbol::new(&env, "delivery_created"),),
    (delivery_id, sender),
);
```

| Event component | Value |
|---|---|
| Event topic | `delivery_created` |
| First event data item | Generated `delivery_id` |
| Second event data item | Sender address |

The event allows external applications and indexers to discover newly created delivery records.

## Delivery Creation and Escrow Ordering

The current `create_delivery` implementation does not call the escrow contract.

It creates and stores the delivery record independently. The escrow contract exposes a separate `create_escrow` entry point that accepts the sender, recipient, driver, delivery ID, token address, and amount.

A typical integration therefore follows this sequence:

1. Initialize the escrow contract.
2. Initialize the delivery contract with the escrow contract address.
3. Call `create_delivery` with the sender, recipient, and metadata.
4. Capture the returned `DeliveryId`.
5. Create the corresponding escrow record through `escrow_contract::create_escrow`, using the same delivery ID and the appropriate escrow parameters.
6. Continue with driver assignment and the delivery lifecycle only after the required delivery and escrow records are successfully established.

The escrow contract's `create_escrow` function independently requires sender authorization, transfers the specified token amount into escrow, stores the escrow record in the `Locked` state, and emits its escrow-funded event.

### Ordering and atomicity considerations

Because delivery creation and escrow creation are separate contract invocations in the current implementation, an integration must handle the possibility that one operation succeeds while the other fails.

For example, if `create_delivery` succeeds but the later escrow creation fails, the delivery record remains created unless a separate recovery or cancellation process handles it.

Do not assume that creating a delivery automatically locks funds or that the two separate calls are atomic as one operation.

The delivery ID returned by `create_delivery` must be reused as the escrow delivery ID so that the records refer to the same delivery.

## Failure Conditions

| Condition | Result |
|---|---|
| Sender does not authorize the transaction | Authorization failure |
| Persistent counter cannot be read or updated | Storage/invocation failure |
| Delivery record cannot be stored | Storage/invocation failure |

The current function does not include an explicit validation step for matching `metadata.delivery_id` with the generated ID.

## Summary

`create_delivery` requires sender authorization, increments the persistent delivery counter, creates a `Pending` delivery record, stores the supplied cargo and delivery metadata, extends the record TTL, emits `delivery_created`, and returns the generated `DeliveryId`. Escrow creation is a separate operation and must use the same ID.
